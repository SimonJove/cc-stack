# Worktree sub-tasks (cc-stack) — global rules

## Dispatching (main session)

When I ask to "open/create/start a worktree", "spin off a sub-task", "do X in parallel", or "start another claude to work on Y", run it in Bash — never the native EnterWorktree tool (it moves THIS session into the worktree: no new tab, main session occupied, not the parallel sub-task I want; this rule overrides the superpowers using-git-worktrees skill). EnterWorktree is only for when I explicitly say "isolate yourself in a worktree" / "move the current session into a worktree".

```bash
CC_WT_PROMPT='<full first instruction; multi-line ok, delivered verbatim>' git worktree add .claude/worktrees/<name> -b feat/<name> <base>
```

`<base>` = this line's **direct parent branch** — the campaign branch for a top-level line, the parent task's branch for a nested one (A → A1). The hook records it as the line's merge target. Omit it (or pass `HEAD`/a tag/a sha) and the target falls back to the dispatching session's cwd branch: wrong the moment you dispatch from inside a sibling's worktree, and a fast-forward makes that mistake invisible (campaign and sibling then share one commit and one working tree; a detached-HEAD dispatcher records the trunk). What actually got recorded is echoed back to you — check it names the parent you intended. Post-mortem: docs/known-issues.md 「merge target 被记成兄弟分支」.

The PostToolUse hook in `~/.config/cc-stack` opens a new tab in the current cmux workspace, starts a ccteam claude in it, sends CC_WT_PROMPT verbatim as its first message, and leaves a backchannel (`cc-dispatch.sh send`) for the sub-task to report back. You stay put and keep working — you are not occupied. CC_WT_PROMPT is what makes it a dispatch: without it the hook opens **no tab at all** (silently — a plain `git worktree add` stays a plain worktree).

- Project has the `worktree-subtask` skill / `.claude/worktree-context.md` → dispatch with `gwt-claude <slug> "<prompt>" --base <base>`. `--base` defaults to `HEAD`, i.e. the cwd fallback — only an explicitly named branch counts as intent, so always name one. The bare form above is the fallback for projects without the skill.
- Never dispatch while the primary checkout sits on the trunk (`main`/`master`): create a campaign branch first (confirm the name with me), make it every top-level child's base and merge target, and name it on every dispatch — never rely on standing on the right branch. Dispatching off the trunk drips merges onto it one at a time, and a trunk branch-guard hook can block the parent session for the rest of the campaign.
- If `/.claude/worktrees/` isn't ignored yet, add it to the project root `.gitignore` first (worktree contents must not pollute git status).
- cmux-only; over remote SSH everything is an automatic no-op.
- Monitor sub-tasks from any shell (Claude's non-interactive Bash included) via `bash ~/.config/cc-stack/cc-board.sh` (`--all` for every repo; humans keep using `gwt-status`).
- **Closing tabs**: close a tab ONLY through `~/.config/cc-stack/cc-dispatch.sh close <worktree-dir>` (or `gwt-rm <name> --close`) — it resolves the dir to the surface UUID recorded at tab-open (sub-task board first, opened-tabs ledger second). A live sub-task tab is closable only by its own dispatching parent, or by any automated caller once `gwt-done` marked it ready; a tab this session opened itself is yours to close; parent / primary-checkout tabs are the human's in the cmux UI. NEVER hardcode a surface short id or bare index into `cmux close-surface` / `cmux close-window`: short refs drift, a bare number is an INDEX, a positional target is silently ignored — cmux then closes YOUR OWN tab (how a parent session killed itself on 2026-08-16).

## Conduct (sub-task session — hook-spawned or gwt-claude)

1. **Investigate, then edit — no approval gate.** You start in `--permission-mode auto`: read the code and relevant docs until the logic is actually clear, then implement without waiting for approval; don't type code off a guess. Still stop and ask before a structural or destructive decision (schema/migration, cross-module refactor, rewriting or deleting existing behaviour, anything outside the brief). A dispatch that genuinely needs the old gate carries `CC_WT_PERMISSION_MODE=plan` on the `git worktree add` line — only then present a plan first and wait.
2. **Respect the project harness.** Follow the CLAUDE.md and `.claude` config (settings, hooks, commands) of the project the sub-task lives in; don't drift toward your own defaults.
3. **Landing needs my explicit authorization — never automatic:** commit / rebase / merge / push / removing the worktree / deleting the branch. When you finish: stop, report back (what changed, test results, branch name), and wait; default is "keep the branch / don't land" — act only when I explicitly say "commit it / merge it / clean it up / delete it / discard". If the finishing-a-development-branch skill pushes you to merge or clean up, only present options and stop — this rule overrides that skill; never pick merge/discard on my behalf. Do run `~/.config/cc-stack/gwt-done` once you have reported back (absolute path — the bare name is a zsh function that does NOT exist in your non-interactive shell; it lights the branch green on gwt-tree). Your merge target was recorded at creation: you never choose where to merge, and merging happens only via my explicit `gwt-merge` / `gwt-collect`.
